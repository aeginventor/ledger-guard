# 설계 결정 로그

각 항목은 번호, 결정, 대안, 이유, 사용자 확인 필요 여부로 적습니다. "사용자 확인 필요: 예"는 작성자(김산)가 아직 검토하지 않은 결정입니다. 명세에 이미 적혀 있던 결정은 "아니오"로 표시했습니다.

## 1. 부가세 원 미만은 버린다

- 결정: `floor(supplyAmount × 10 / 100)`. 공급가액 12,345원이면 부가세 1,234원
- 대안: 반올림, 올림
- 이유: 명세가 버림을 지정했다. 근거 조문으로 국고금관리법 제47조를 적었으나 확인하지 않았다
- 사용자 확인 필요: 예 (조문 확인)

## 2. FAIL 전표도 저장한다

- 결정: FAIL 판정 전표는 `REJECTED` 상태로 저장하고 사유를 `validation_finding`에 남긴다. HTTP 201
- 대안: 400이나 422로 거부하고 저장하지 않음
- 이유: 어떤 초안이 왜 거부됐는지 추적할 수 있어야 규칙과 초안 품질을 함께 개선할 수 있다. 명세가 감사 추적을 요구했다
- 사용자 확인 필요: 아니오

## 3. LLM 작성기는 기본 비활성, fixture 작성기가 기본

- 결정: `JournalDrafter` 구현 가운데 `FixtureJournalDrafter`가 기본이다. OpenAI 작성기는 `OPENAI_API_KEY`가 있을 때만 빈으로 등록되고 `LEDGER_GUARD_DRAFTER=openai`로 골라야 쓰인다. 응답 `drafter` 필드에 어떤 작성기가 만들었는지 적는다
- 대안: LLM을 기본으로 두고 키가 없으면 오류
- 이유: 키 없이도 전체 흐름과 테스트가 돌아야 한다. 실제 호출을 하지 않았다는 사실을 응답에서 바로 알 수 있어야 한다
- 사용자 확인 필요: 아니오

## 4. 테스트는 H2 PostgreSQL 모드, Testcontainers는 쓰지 않는다

- 결정: `jdbc:h2:mem:ledger;MODE=PostgreSQL`. Flyway SQL은 두 DB에서 모두 도는 표준 SQL만 쓴다(JSONB, 배열, 시퀀스 전용 문법 금지)
- 대안: Testcontainers로 실제 PostgreSQL 사용
- 이유: CI가 Docker 없이도 돌아야 한다는 명세. PostgreSQL 고유 동작은 compose 실행으로만 확인했다
- 사용자 확인 필요: 아니오

## 5. REVIEW 전표 승인에는 사유가 필수

- 결정: 재검증 결과가 REVIEW이면 `reason`이 비어 있을 때 409. 사유가 있으면 승인하고 `approval_reason`에 남긴다
- 대안: REVIEW도 사유 없이 승인 허용
- 이유: 검토가 필요하다고 판정한 전표를 누가 왜 넘겼는지 남겨야 한다
- 사용자 확인 필요: 아니오

## 6. 계정과목 코드는 3자리 숫자, 30개, 사용 중지 계정 1개 포함

- 결정: 한국 중소기업에서 널리 쓰이는 3자리 코드 체계를 참고했다(101 현금, 135 부가세대급금, 255 부가세예수금, 401 매출, 813 기업업무추진비 등). 150 제품은 상품 매매업 기준으로 쓰지 않는 계정의 예시로 `active=false`다. 규칙이 참조하는 특수 계정(135, 255, 813)은 `LedgerAccounts` 상수에 모았다
- 대안: 4자리 코드, 회사별 자유 코드, 계정 이름으로 참조
- 이유: 코드로 참조해야 이름 변경(접대비 → 기업업무추진비)에 흔들리지 않는다. 코드 값 자체는 회사마다 다를 수 있다
- 사용자 확인 필요: 예 (코드와 이름이 작성자가 생각하는 표준과 맞는지)

## 7. 시산표는 뷰가 아니라 집계 쿼리, 해당 월만 집계

- 결정: `ledger_entry`를 계정과 차대로 group by 하는 JPQL 쿼리 하나. 요청한 월에 전기된 항목만 집계하고 이월 잔액은 없다
- 대안: DB 뷰, 월별 집계 테이블, 누적 잔액
- 이유: 데이터가 작고 원장이 유일한 진실이어야 한다. 누적 잔액과 이월은 결산 기능과 함께 설계해야 해서 뺐다
- 사용자 확인 필요: 예 (월 단위 집계가 의도와 맞는지)

## 8. R04에서 `vatType=NA`도 부가세 라인을 금지한다

- 결정: 명세는 면세와 영세율만 언급했지만 `NA`(급여, 자본금, 채권 회수 등)에도 부가세 라인이 있으면 FAIL
- 대안: `NA`는 검사하지 않음
- 이유: 부가세 대상이 아닌 거래에 부가세 라인이 붙는 것은 LLM 초안에서 흔한 실수이고 틀린 것이 분명하다
- 사용자 확인 필요: 예

## 9. R09에서 현금영수증은 적격증빙으로 본다

- 결정: `evidenceType=NONE`일 때만 REVIEW. `CASH_RECEIPT`는 세금계산서, 카드와 같이 적격증빙으로 취급한다
- 대안: 명세의 "NONE/CASH" 표현대로 현금영수증도 REVIEW
- 이유: 법인세법상 현금영수증은 적격증빙에 포함된다고 이해했다(확인 필요). 명세의 "CASH"는 영수증 없는 현금 지출로 해석했고 그 경우는 `NONE`에 해당한다
- 사용자 확인 필요: 예

## 10. R06의 세액 분리 라인 요구는 과세 거래에만 적용

- 결정: 세금계산서 증빙이라도 `vatType`이 `ZERO_RATED`나 `EXEMPT`이면 부가세 라인을 요구하지 않는다
- 대안: 세금계산서면 항상 부가세 라인 요구
- 이유: 영세율 세금계산서는 세액이 0이고 R03이 0원 라인을 금지하므로 두 규칙이 충돌한다
- 사용자 확인 필요: 예

## 11. R05의 매출과 매입 판별은 수익 계정 라인 유무로 한다

- 결정: 부가세가 아닌 라인에 `REVENUE` 유형 계정이 있으면 매출 거래, 없으면 매입 거래
- 대안: 거래 유형 필드를 요청에 추가, 부가세 라인 자체의 계정으로 판별
- 이유: 요청 필드를 늘리지 않고 전표만으로 판별할 수 있다. 환입과 환출은 다루지 못한다. 잡이익도 수익이라 매출로 본다(semantic_misses S02)
- 사용자 확인 필요: 예

## 12. R10 중복 검사는 REJECTED 전표를 제외한다

- 결정: 같은 일자, 거래처, 차변 합계의 기존 전표 가운데 `REJECTED`는 비교하지 않는다
- 대안: 모든 상태 비교
- 이유: FAIL로 저장된 전표를 고쳐 다시 올릴 때 중복으로 잡히면 흐름이 막힌다
- 사용자 확인 필요: 예

## 13. 승인은 규칙을 다시 돌리고, 409로 끝나면 전표를 바꾸지 않는다

- 결정: 승인 요청마다 전체 규칙을 다시 실행한다. FAIL이거나 REVIEW인데 사유가 없으면 409를 돌려주고 트랜잭션을 롤백해 전표 상태와 사유를 바꾸지 않는다. 재검증 결과는 409 응답 본문에만 담는다
- 대안: 저장 시점 판정을 믿고 승인, 또는 실패 시 전표를 REJECTED로 갱신
- 이유: 저장 뒤 기간이 마감될 수 있다. 실패한 승인이 전표를 바꾸면 조회 결과가 승인 시도 여부에 따라 달라져 혼란스럽다
- 사용자 확인 필요: 예

## 14. 매입세액 불공제는 자동 판별하지 않는다

- 결정: 기업업무추진비처럼 매입세액이 공제되지 않는 거래는 총액을 비용으로 적고 `vatType=NA`로 둔다. fixture `entertainment`도 그렇게 만든다
- 대안: 813 계정이 있으면 부가세 라인을 금지하는 규칙 추가
- 이유: 불공제 사유는 기업업무추진비 외에도 많고(비영업용 승용차 등) 하루 안에 정확히 정리할 수 없었다. 규칙 하나로 일부만 다루면 오히려 오해를 만든다
- 사용자 확인 필요: 예

## 15. 금액은 BigDecimal로 받고, 저장할 때는 원 미만을 버린다

- 결정: API 요청의 `amount`는 `BigDecimal`. 소수가 오면 R03이 FAIL 사유를 남기고 전표는 REJECTED로 저장되며 `voucher_line.amount`(BIGINT)에는 원 미만을 버린 값이 들어간다. Jackson의 float→int 암묵 변환은 껐다
- 대안: `long`으로 받아 소수 요청을 400으로 거부
- 이유: 소수 금액은 LLM 초안의 흔한 실수이고 규칙 사유로 남기는 편이 추적에 좋다. 저장 컬럼은 명세대로 정수를 유지한다
- 사용자 확인 필요: 예

## 16. APPROVED 상태를 거치지 않고 승인 즉시 POSTED

- 결정: 승인과 전기가 한 트랜잭션이다. `VoucherStatus.APPROVED`는 열거형에 남겨 두었지만 쓰지 않는다
- 대안: 승인(APPROVED) 뒤 별도 전기 단계
- 이유: 명세가 승인 시 LedgerEntry 생성을 요구했고, 승인과 전기를 나눌 운영 요구가 아직 없다
- 사용자 확인 필요: 예

## 17. 시간대는 Asia/Seoul로 고정한 Clock을 주입한다

- 결정: `ledger-guard.zone`(기본 Asia/Seoul)으로 `Clock` 빈을 만들고 R08과 생성, 승인, 마감 시각이 이 Clock을 쓴다. 시각은 밀리초로 잘라 저장한다
- 대안: 서버 기본 시간대, UTC
- 이유: 컨테이너는 UTC가 기본이라 자정 전후에 "미래 일자" 판정이 흔들린다. 밀리초 절단은 Linux의 나노초 시각이 DB를 거치며 잘려 응답이 달라지던 CI 실패를 고친 것이다
- 사용자 확인 필요: 예

## 18. OpenAI 작성기는 Spring AI 대신 RestClient로 만든다

- 결정: Spring Boot의 `RestClient`로 OpenAI chat completions JSON 모드를 직접 호출하는 어댑터. `OPENAI_API_KEY`가 비어 있으면 빈을 만들지 않는다. 응답 JSON 파싱에 실패하면 `DraftResult.problems`에 담아 R11이 FAIL로 기록한다. 실제 호출은 하지 않았다
- 대안: Spring AI OpenAI starter
- 이유: 의존성을 늘리지 않고 요청과 응답 형식을 코드에서 그대로 볼 수 있다. 프롬프트와 파싱 실패 처리를 단위 테스트로 고정할 수 있다
- 사용자 확인 필요: 예
