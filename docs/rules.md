# 규칙 상세

규칙은 `io.github.aeginventor.ledgerguard.validation.rules` 패키지의 독립 클래스 13개입니다. 모두 `ValidationRule`을 구현하고 `ValidationEngine`이 코드 순으로 끝까지 실행합니다. 어느 규칙도 다른 규칙의 결과를 보지 않습니다. 판정은 FAIL이 하나라도 있으면 FAIL, 없고 REVIEW가 있으면 REVIEW, 둘 다 없으면 PASS입니다.

규칙이 보는 입력은 `VoucherData`(전표 일자, 설명, 거래처, 사업자등록번호, 증빙 종류, 부가세 종류, 공급가액, 라인 목록)와 `ValidationContext`(계정과목 조회, 기간 마감 여부, 중복 조회, 오늘 날짜, 단계, 초안 생성 문제 목록)입니다. 라인 금액은 `BigDecimal`로 받아 소수와 음수도 규칙이 사유와 함께 거부합니다.

세법 조문 번호는 작성자가 직접 확인해야 합니다. "확인 필요"가 붙은 조문은 작성자가 아직 닫지 않았습니다. 조문 원문을 읽어 대조한 메모는 [legal-basis.md](legal-basis.md)에 있습니다.

단계는 셋입니다. `DRAFT`는 초안을 저장 없이 판정할 때, `SAVE`는 전표를 저장할 때, `APPROVE`는 승인할 때입니다. 승인 단계는 저장 단계의 규칙을 전부 다시 돌리고 R12를 더합니다. 역분개 전표(`reversalOfId`가 있는 전표)에는 R05와 R10을 적용하지 않습니다. 원전표의 차대를 그대로 뒤집은 것이라 R05의 방향 판정이 뒤집히고, R10이 찾는 중복은 원전표 자신이기 때문입니다.

## R01 BALANCED (FAIL)

- 입력: 모든 라인의 차변 금액 합계와 대변 금액 합계
- 판정: 두 합계가 다르면 FAIL. 금액이 없는 라인은 0으로 더한다(R03이 따로 사유를 남긴다)
- 예시: 차변 소모품비 100,000 + 부가세대급금 10,000, 대변 현금 100,000 → FAIL "차변 합계 110000원과 대변 합계 100000원이 다르다"
- 근거: 복식부기 대차평균의 원리

## R02 ACCOUNT_VALID (FAIL)

- 입력: 각 라인의 계정코드, 계정과목표
- 판정: 계정코드가 없거나, 계정과목표에 없거나, `active=false`이면 라인마다 FAIL
- 예시: 코드 `999` → "계정과목표에 없다". 코드 `150 제품`(사용 중지) → "사용 중지된 계정이다"
- 근거: 계정과목표(`account` 테이블, Flyway V2 시드)

## R03 AMOUNT_POSITIVE_INT (FAIL)

- 입력: 각 라인의 금액
- 판정: 금액이 없으면 FAIL, 소수점 아래가 0이 아니면 FAIL, 0 이하이면 FAIL
- 예시: `1000.5` → "원 단위 정수가 아니다". `-100000` → "1원 이상이어야 한다". `1000.00`은 통과
- 근거: 전표 금액은 원 단위 정수

## R04 VAT_AMOUNT (FAIL)

- 입력: `vatType`, `supplyAmount`, 부가세 라인(계정과목표의 `vatRelated=true`인 계정, 즉 135 부가세대급금과 255 부가세예수금)
- 판정
  - `TAXABLE`이고 `supplyAmount`가 있으면 부가세 라인 합계가 `floor(supplyAmount × 10 / 100)`과 같아야 한다. 다르면 FAIL. `supplyAmount`가 없으면 검사하지 않는다
  - `EXEMPT`, `ZERO_RATED`, `NA`이면 부가세 라인이 하나라도 있으면 FAIL
- 예시: 공급가액 12,345원 → 기대 부가세 1,234원. 1,235원(반올림)이면 FAIL. 면세 도서 구입에 부가세대급금 4,500원 → FAIL
- 근거: 부가가치세법 제30조(세율 10%). 원 미만 버림은 국고금관리법 제47조(확인 필요)
- 한계: 기업업무추진비처럼 매입세액이 공제되지 않는 거래(부가가치세법 제39조, 확인 필요)는 자동으로 가려내지 않는다. 총액을 비용으로 적고 `vatType=NA`로 두어야 통과한다

## R05 VAT_ACCOUNT_SIDE (FAIL)

- 입력: 부가세 라인, 나머지 라인의 계정 유형
- 판정: 부가세가 아닌 라인 가운데 수익(`REVENUE`) 계정이 하나라도 있으면 매출 거래, 아니면 매입 거래로 본다. 매출 거래의 부가세 라인은 255 부가세예수금 대변, 매입 거래의 부가세 라인은 135 부가세대급금 차변이어야 한다. 계정이나 차대가 다르면 라인마다 FAIL. 부가세 라인이 없으면 검사하지 않는다
- 예시: 소모품 매입에 부가세예수금 차변 → FAIL. 매출에 부가세대급금 차변 → FAIL
- 근거: 부가가치세법 제37조 납부세액 계산에서 매출세액과 매입세액을 구분(확인 필요)
- 한계: 매출 환입이나 매입 환출처럼 반대 방향 거래는 다루지 않는다. 역분개 전표에는 적용하지 않는다

## R06 TAX_INVOICE_REQUISITES (FAIL)

- 입력: `evidenceType`, `counterpartyBizNo`, `vatType`, 라인
- 판정: `evidenceType=TAX_INVOICE`일 때만 적용
  - 사업자등록번호가 없으면 FAIL. 하이픈을 뺀 10자리 숫자가 아니면 FAIL. 체크섬이 틀리면 FAIL
  - `vatType=TAXABLE`이면 부가세 라인과 부가세가 아닌 라인이 모두 있어야 한다. 아니면 FAIL
- 사업자등록번호 체크섬: 앞 9자리에 가중치 1, 3, 7, 1, 3, 7, 1, 3, 5를 곱해 더하고, 9번째 자리와 5의 곱을 10으로 나눈 몫을 더한 뒤, (10 − 합 % 10) % 10 이 10번째 자리와 같아야 한다. 테스트와 골든셋의 번호는 이 알고리즘으로 만든 가상 번호이며 실제 기업의 번호가 아니다
- 예시: `123-45-67890` → 체크섬 실패. `123-45-67891` → 통과. 영세율 세금계산서는 세액이 0이므로 부가세 라인을 요구하지 않는다
- 근거: 부가가치세법 제32조 제1항 세금계산서 필요적 기재사항(확인 필요)

## R07 PERIOD_OPEN (FAIL)

- 입력: 전표 일자, 회계기간 마감 여부
- 판정: 전표 일자의 연월이 `accounting_period.closed=true`이면 FAIL. 저장과 승인 양쪽에서 검사한다
- 예시: 2026-08 마감 뒤 2026-08-20 전표 → FAIL "2026-08 기간은 이미 마감되었다"
- 근거: 회계기간 마감

## R08 DATE_NOT_FUTURE (FAIL)

- 입력: 전표 일자, 오늘(`Clock` 주입, 기본 시간대 Asia/Seoul)
- 판정: 전표 일자가 오늘보다 뒤이면 FAIL. 일자가 없어도 FAIL
- 예시: 오늘이 2026-10-11일 때 2026-10-12 → FAIL
- 근거: 발생주의 회계. 아직 일어나지 않은 거래는 기록하지 않는다

## R09 ENTERTAINMENT_EVIDENCE (REVIEW)

- 입력: 813 기업업무추진비 차변 라인 합계, `evidenceType`
- 판정: 합계가 30,000원을 넘고 `evidenceType=NONE`이면 REVIEW. 세금계산서, 카드, 현금영수증은 적격증빙으로 보아 통과시킨다. 30,000원 이하이면 증빙이 없어도 통과
- 예시: 50,000원 현금 지출에 증빙 없음 → REVIEW. 50,000원 카드 → 통과. 30,000원 증빙 없음 → 통과
- 근거: 법인세법 제25조 제2항, 같은 법 시행령 제41조. 3만원 초과 기업업무추진비는 적격증빙이 없으면 손금불산입(확인 필요)

## R10 DUPLICATE_SUSPECT (REVIEW)

- 입력: 전표 일자, 거래처 이름, 차변 합계, 기존 전표 조회
- 판정: 같은 일자, 같은 거래처, 같은 차변 합계의 전표가 이미 있으면 REVIEW. REJECTED 상태의 전표는 비교 대상에서 뺀다(고쳐서 다시 올리는 흐름을 막지 않기 위해). 승인 시 재검증에서는 자기 자신을 뺀다. 거래처 이름이 없으면 검사하지 않는다
- 예시: 2026-10-02 가상문구 110,000원 전표가 있을 때 같은 조건의 전표 → REVIEW
- 근거: 이중 기표 방지

## R11 DRAFT_SCHEMA (FAIL)

- 입력: 단계(`DRAFT`, `SAVE`, `APPROVE`), 초안 생성 문제 목록, 라인
- 판정: `DRAFT` 단계에서만 적용. 작성기가 넘긴 문제(예: JSON 파싱 실패, 맞는 fixture 없음)는 그대로 FAIL. 라인이 2개 미만이면 FAIL. 라인에 `accountCode`, `side`, `amount` 가운데 빠진 것이 있으면 라인마다 FAIL
- 예시: 라인 1개짜리 초안 → FAIL "초안 라인이 1개다". fixture가 없는 설명 → FAIL "초안 생성 실패: 거래 설명과 맞는 고정 초안이 없다"
- 근거: 초안 스키마

## R12 PREPARER_NOT_APPROVER (FAIL)

- 입력: 단계, 전표의 작성자(`preparer`), 승인 요청의 승인자(`approver`)
- 판정: `APPROVE` 단계에서만 적용. 작성자와 승인자가 앞뒤 공백과 대소문자를 무시하고 같으면 FAIL. 어느 한쪽이 비어 있으면 검사하지 않는다(전표 저장은 작성자를 필수로 받으므로 실제로는 승인자가 비었을 때뿐이다)
- 예시: 작성자 "김작성"이 승인자 "김작성"으로 승인 → 409 "작성자 김작성이(가) 자기 전표를 승인할 수 없다". 승인자를 "박승인"으로 바꾸면 통과
- 근거: 내부통제의 직무 분리(전표 작성과 승인을 다른 사람이 한다)
- 한계: 인증이 없어 두 이름은 요청 본문의 문자열이다. 이름만 바꿔 적으면 우회된다. 인증과 역할을 붙이는 것이 다음 단계다

## R13 EVIDENCE_MATCHES_VAT_TYPE (REVIEW)

- 입력: `evidenceType`, `vatType`
- 판정: `EXEMPT`인데 증빙이 `TAX_INVOICE`이면 REVIEW. `TAXABLE`이나 `ZERO_RATED`인데 증빙이 `INVOICE`(계산서)이면 REVIEW. 카드, 현금영수증, 증빙 없음, `NA`는 검사하지 않는다
- 예시: 면세 도서 구입에 세금계산서 → REVIEW "면세 거래의 증빙이 세금계산서다". 과세 사무용품 구입에 계산서 → REVIEW
- 근거: 부가가치세법 제32조 제1항 본문이 면세 재화 또는 용역의 공급을 세금계산서 발급 대상에서 뺀다([legal-basis.md](legal-basis.md)). 계산서는 법인세법 제121조와 소득세법 제163조(확인 필요)
- 유래: 조문 원문을 읽고 R06의 빈칸으로 찾아 더한 규칙이다. 증빙 종류에 `INVOICE`(계산서)를 함께 추가했고, R09는 계산서를 적격증빙으로 본다(법인세법 제25조 제2항 제2호)

## 규칙이 보지 않는 것

- 계정 선택이 거래의 실질과 맞는지. `semantic_misses.json`의 5건이 모두 PASS로 나온다. 상세는 [evaluation.md](evaluation.md)
- 공급가액이 라인 금액과 맞는지. R04는 부가세 라인만 본다
- 거래처가 실제로 존재하는지, 사업자등록번호가 그 거래처의 것인지. 체크섬만 본다
- 원천징수세액, 4대보험 같은 급여 관련 계산
- 기업업무추진비 가운데 경조금은 기준이 3만원이 아니라 20만원(법인세법 시행령 제41조 제1항 제1호)인데, 전표에 경조금 여부가 없어 R09는 3만원만 적용한다
- 신용카드가 법인 명의인지(같은 시행령 제41조 제6항). `evidenceType=CARD`는 법인카드와 개인카드를 구분하지 않는다
- 계정 선택을 같은 유형 안에서 바꾼 전표. 변이 평가의 SAME_TYPE_ACCOUNT_SWAP 27건이 전부 PASS로 나온다. 상세는 [evaluation.md](evaluation.md)
