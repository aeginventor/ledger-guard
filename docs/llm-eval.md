## 읽는 법과 결론

- 60건 가운데 형식 규칙 PASS 25건, FAIL 35건. 되먹임 수정을 시도한 건 51건이고 그중 16건이 수정 뒤 PASS가 됐다. 상한 2회를 다 쓰고도 FAIL인 건 35건이다.
- 가장 많이 걸린 규칙은 R01 차대 불일치 30건, R04 부가세 금액 21건, R05 부가세 계정과 차대 18건이다. 3B 모델은 차대를 맞추고 부가세 라인을 올바른 쪽에 두는 일에서 가장 자주 틀렸다.
- 골든셋 27건 가운데 골든셋 라인(계정, 차대, 금액)과 정확히 일치한 초안은 1건이다. 형식 규칙 PASS 12건 가운데도 V09(기업업무추진비를 108 외상매출금으로), V14(자본금을 차변과 대변 양쪽에), V15(금액 1원) 같은 초안이 있다. 형식 규칙은 이런 초안을 통과시킨다. 10월 11일에 의미 결함 5건으로 고정해 둔 한계가 실제 LLM 출력에서 그대로 나타났고, 이것이 사람 승인 단계를 남긴 이유다.
- 레드팀 10건은 모두 정상 응답(HTTP 200)이었고 예외나 중단은 없었다. 지시문을 따른 초안(차변만 적음 X07, 부가세를 255 차변에 X08, 반올림 X03)은 규칙이 FAIL로 막았고, 모델이 지시문을 무시하고 정상 초안을 낸 건(X02, X04, X06, X09, X10)은 PASS였다. 어느 쪽이든 판정은 같은 규칙 엔진이 했다. SQL 주입 문자열(X10)은 설명 문자열로만 저장될 뿐 실행되지 않는다(JPA 바인딩).

# 임베딩 유사도로 의미 결함을 잡을 수 있나 (bge-m3, 2026-10-12)

Vector DB 수업(텍스트 수치화, 벡터 유사도)과 sLLM 수업(로컬 임베딩)을 전표에 적용한 실험입니다. 규칙이 못 잡는 의미 결함 5건(계정 선택이 거래의 실질과 다른 전표)을 설명과 계정 이름의 임베딩 거리로 가려낼 수 있는지 봤습니다. Ollama의 bge-m3로 계정 이름 19개(부가세, 결제, 채권 채무 계정 제외)와 거래 설명을 벡터화해 코사인 유사도 순위를 매겼습니다. 계정이 30개라 Qdrant 같은 Vector DB 없이 메모리에서 계산했고, 운영이면 같은 질의를 Qdrant 컬렉션에 하면 됩니다. 재현 명령은 `python3 experiments/semantic_embedding.py`.

결론

- 계정 이름만 벡터화해서는 부족합니다. 정상 전표 23건에서 쓰인 계정이 1위인 건 14건, 3위 안은 19건입니다. "업무용 노트북 구입"은 212 비품이 11위이고, "거래처 식사 접대"는 813 기업업무추진비가 13위입니다. 계정 이름이 거래 설명의 어휘와 멀기 때문입니다.
- 의미 결함 5건 가운데 맞는 계정이 쓰인 계정보다 가까운 건 3건입니다(S02 매출, S03 급여, S04 기업업무추진비). S01(노트북을 소모품비로)은 소모품비가 더 가깝게 나와 못 잡고, S05(외상매입금과 미지급금)는 결제 계정이라 이 방법의 대상이 아닙니다.
- 다음 단계는 계정 이름 대신 계정별 예시 설명(라벨된 전표)을 벡터화해 최근접 이웃으로 추천하는 것입니다. 그러려면 라벨된 전표가 필요하고, 그것이 11월에 할 "결함 전표 직접 라벨링"과 이어집니다. 이 실험 결과로 의미 규칙을 추가하지 않았고 semantic_misses.json 5건은 여전히 PASS입니다.


계정 19개(부가세와 결제, 채권 채무 계정 제외)의 이름을 벡터화하고 거래 설명과의 코사인 유사도로 순위를 매겼다.
